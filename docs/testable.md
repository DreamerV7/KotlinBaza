# Анализ тестопригодности

## Архитектура и выбранные проверки

Проект уже отделяет бизнес-логику от хранения данных через `UserRepository`, `ResourceRepository`, `PermissionRepository` и `PasswordHasher`. Зависимости передаются через конструкторы. Для изолированных проверок используются небольшие реализации этих интерфейсов в тестах, без сети, файловой системы и дополнительных mock-библиотек.

| Класс | Проверяемое поведение |
|---|---|
| `Authenticator` | Неизвестный пользователь, неверный хеш, успешная авторизация, передача пароля и соли; отсутствие хеширования для неизвестного пользователя |
| `AccessPolicy` | Точное право, наследование от предка, запрет наследования к родителю и соседу, границы сегментов, другой пользователь/действие, пустой список прав |
| `ResourcePathValidator` | Пустой путь, пустые сегменты, допустимые символы, недопустимые символы, длина сегмента 20/21 |
| `ResourceActionHandler` | Неверный формат, отрицательный объём, отсутствующий ресурс, превышение объёма, отказ в доступе, объёмы 0/1/99/100 при лимите 100; порядок ошибок |
| `ActionRegistry`, `CheckAccessUseCase` | Неизвестное действие, передача аргументов выбранному обработчику и возврат его результата |
| `Sha256PasswordHasher` | Известные SHA-256 векторы для `abc` и пустой строки, влияние соли |
| `AppContainer`, `AuthenticateUserUseCase` | Дополнительные интеграционные проверки сборки зависимостей, штатного пользователя и всех трёх действий |
| `AccessResult.toExitCode` | Соответствие всех результатов документированным кодам завершения |

## Изменения проекта

Рефакторинг бизнес-логики не потребовался: существующих интерфейсов достаточно для изоляции зависимостей. Исходники `src` не менялись.

Добавлены JUnit 5, тесты в `tests`, тестовая библиотека IDEA и отметка тестового каталога. Markdown перенесён в `docs`, Bash-скрипты — в `scripts`. Скрипты сами переходят в корень проекта, учитывают разделитель classpath Windows/Linux. Артефакты новой сборки пишутся в игнорируемый `out`, чтобы не менять исходный отслеживаемый `app.jar`. У CLI smoke-скрипта добавлен ненулевой код завершения при провале, обновлены пути. CI запускает оба набора проверок и сохраняет XML-результаты.

## Результаты выполнения тестов

Локальная проверка: JDK 17.0.12, Kotlin 2.4.20, JUnit Platform 1.12.2 / Jupiter 5.12.2, Windows и Git Bash.

- `bash scripts/test.sh`: **47 выполнено, 47 успешно, 0 пропущено, 0 ошибок** (включая параметризованные случаи).
- `bash scripts/build.sh`: сборка успешна; прямой запуск `java -jar out/app.jar` для штатного доступа вернул код 0.
- `bash scripts/smoke-test.sh`: **10 выполнено, 10 успешно**, включая коды завершения 0–8 и обе формы справки.

Примеры сценариев:

- `shouldRejectUnknownLoginWithoutHashingPassword`: при неизвестном логине хешер не вызывается.
- `shouldHashSuppliedPasswordWithStoredSalt`: проверяется соль найденного пользователя, исходный пароль и единственный вызов хешера.
- `shouldNotMatchPartialSegment`: право на `A.B` не распространяется на `A.BC`.
- `shouldReportExceededVolumeBeforeCheckingPermission`: превышение лимита возвращается раньше отказа в правах, как в текущей реализации.
- `shouldAllowVolumeWithinInclusiveLimits`: нулевой объём и ровно максимальный объём разрешены при наличии прав.
- `shouldMatchKnownSha256VectorWithSaltBeforePassword`: проверяется известный хеш, а не повторение алгоритма в тесте.

### Что не покрыто отдельными модульными тестами

`main` использует `exitProcess`, стандартный вывод и CLI-парсер: проверяется отдельными процессами в десяти smoke-сценариях. Не все ошибки парсера и варианты аргументов покрыты; выделение функции CLI, возвращающей код, можно сделать в следующей работе при необходимости расширения тестов.

`InMemoryUserRepository`, `InMemoryResourceRepository`, `InMemoryPermissionRepository` проверяются косвенно через `AppContainer`, отдельные тесты всех записей не добавлены: это статические данные и простые поиски. Data-классы и интерфейсы не содержат самостоятельных алгоритмов. Процент покрытия не измерялся.

## Подготовка к TDD

Для следующего изменения сначала добавить тест ожидаемого поведения и убедиться, что он падает; затем реализовать минимальное изменение и выполнить оба набора проверок. Текущий набор фиксирует уже существующее поведение и сам по себе не означает, что проект разрабатывался по TDD.
