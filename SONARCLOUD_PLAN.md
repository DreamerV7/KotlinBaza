# SonarCloud Integration Plan

## 1. Цель интеграции

SonarCloud — облачный сервис для статического анализа исходного кода. Он помогает находить потенциальные ошибки, уязвимости, проблемы сопровождения и недостатки тестового покрытия.

Цель подключения SonarCloud к проекту — автоматизировать проверку качества Kotlin-кода и получать результаты анализа при обновлении репозитория.

На данном этапе составляется план интеграции. Настройка сервиса и изменение исходного кода в рамках этой лабораторной не выполняются.

## 2. Текущее состояние проекта

Проект представляет собой небольшое консольное приложение на Kotlin.

Особенности текущей сборки:

- используется компилятор Kotlin;
- сборка выполняется скриптом `build.sh`;
- запуск выполняется скриптом `run.sh`;
- тестовые сценарии запускаются через `test.sh`;
- Gradle и Maven не используются;
- исходный код расположен в каталоге `src`;
- зависимости хранятся в каталоге `lib`.

При подключении SonarCloud необходимо учитывать текущий способ сборки и не добавлять Gradle или Maven без отдельной необходимости.

## 3. Подготовительный этап

1. Проверить, что проект находится в GitHub и доступен участникам команды(то есть мне одному, можно считать выполнен).
2. Убедиться, что исходный код и скрипты сборки находятся в репозитории.
3. Проверить успешное выполнение `./build.sh`.
4. Проверить успешное прохождение тестов через `./test.sh`.
5. Уточнить доступность SonarCloud для репозитория и права участника, который будет настраивать интеграцию.

Результат этапа: проект готов к подключению внешнего сервиса анализа.

## 4. Создание проекта в SonarCloud

1. Войти в SonarCloud через поддерживаемый способ авторизации.
2. Подключить GitHub-аккаунт, если это ещё не сделано.
3. Импортировать репозиторий `DreamerV7/KotlinBaza`.
4. Создать проект анализа и проверить настройки организации.
5. Получить токен для запуска анализа, если он требуется выбранным способом интеграции.

Токен нельзя хранить в исходном коде, README или других файлах репозитория. Для автоматического запуска следует использовать секреты GitHub Actions.

## 5. Настройка анализа

1. Проверить актуальную документацию SonarCloud по анализу Kotlin-проектов без Gradle и Maven.
2. Выбрать поддерживаемый способ передачи исходного кода и запуска анализа.
3. Указать каталог исходников `src`.
4. При необходимости указать расположение тестов и исключить из анализа сгенерированные файлы.
5. Убедиться, что в анализ не попадают сторонние библиотеки из `lib` и собранный файл `app.jar`, если они не являются объектами проверки.
6. Настроить параметры проекта согласно актуальной документации выбранного анализатора.

Конкретные параметры запуска нужно определять после проверки поддерживаемого способа анализа. Нельзя считать, что любая команда для Gradle или Maven подойдёт проекту, который собирается через `build.sh`.

## 6. Автоматизация через GitHub Actions

После проверки совместимости выбранного способа анализа можно добавить workflow GitHub Actions.

План действий:

1. Создать workflow в каталоге `.github/workflows`.
2. Настроить запуск при отправке изменений в рабочую ветку и при создании Pull Request.
3. Подготовить среду с необходимой версией JDK и инструментами анализа.
4. Запускать сборку и тесты проекта.
5. Запускать SonarCloud-анализ поддерживаемым способом.
6. Передавать токен через секреты репозитория.
7. Проверить, что результат анализа отображается в SonarCloud и связан с Pull Request.

Конкретный workflow следует создавать только после подтверждения совместимости SonarCloud с текущим способом сборки.

## 7. Проверка результатов

После подключения необходимо проверить следующие показатели:

- Bugs — потенциальные ошибки.
- Vulnerabilities — потенциальные уязвимости.
- Security Hotspots — участки кода, требующие проверки с точки зрения безопасности.
- Code Smells — проблемы читаемости и сопровождения.
- Coverage — покрытие кода тестами, если тесты распознаются анализатором.
- Duplications — дублирование кода.

Особое внимание следует уделить обработке паролей, проверке прав доступа, обработке входных данных и корректности завершения программы.

Результаты статического анализа необходимо рассматривать вместе с результатами тестирования. Отсутствие замечаний не гарантирует полного отсутствия ошибок.

## 8. Критерии успешного подключения

Интеграцию можно считать выполненной, если:

1. SonarCloud успешно получает и анализирует исходный код.
2. Результаты анализа доступны в интерфейсе сервиса.
3. Анализ запускается автоматически для Pull Request.
4. Токен хранится в секретах, а не в исходном коде.
5. Сборка и существующие тесты продолжают работать.
6. При возникновении проблем команда получает понятный результат проверки.

## 9. План действий при обнаружении проблем

1. Проверить ошибки сборки и запуска анализатора.
2. Убедиться, что анализатор поддерживает выбранный способ сборки Kotlin-проекта.
3. Проверить пути к исходникам и настройки исключений.
4. Разобрать найденные ошибки, предупреждения и замечания по безопасности.
5. Приоритизировать исправления по серьёзности и влиянию на приложение.
6. После будущего рефакторинга повторить анализ и сравнить результаты.

## 10. Вывод

SonarCloud планируется использовать для регулярного статического анализа Kotlin-кода и контроля качества изменений через Pull Request. Поскольку проект собирается без Gradle и Maven, способ интеграции необходимо выбирать с учётом актуальных возможностей сервиса. Реализация интеграции относится к следующему этапу и не входит в текущий анализ.
