# SOLID Analysis

## 1. Общая информация

Проект представляет собой консольное приложение на Kotlin для проверки доступа пользователя к ресурсу. Программа принимает логин, пароль, действие, путь к ресурсу и запрашиваемый объём. Затем она проверяет данные пользователя, права доступа и ограничения ресурса.

В рамках лабораторной работы проводится анализ существующего кода и составляется план рефакторинга. Сам код на этом этапе не изменяется.

## 2. Анализ принципов SOLID

### 2.1. SRP — принцип единственной ответственности

**Где находится проблема:** функция `main()` в файле `src/Main.kt`.

**Что не так:** функция выполняет сразу несколько задач:
- обрабатывает аргументы командной строки;
- выводит справку;
- проверяет логин и пароль;
- проверяет формат пути и существование ресурса;
- проверяет объём и права доступа;
- завершает программу с соответствующим кодом возврата.

Из-за этого функция получается большой, а изменение одной части логики может повлиять на другие проверки.

**Предлагаемое решение:** разделить обработку аргументов, авторизацию, проверку ресурсов и проверку прав доступа на отдельные классы или функции.

### 2.2. OCP — принцип открытости/закрытости

**Где находится проблема:** конструкция `when (action)` в функции `main()`.

**Что не так:** при добавлении нового действия потребуется изменять существующий код обработки действий. При увеличении количества действий такая конструкция может стать сложнее для поддержки.

**Предлагаемое решение:** предусмотреть отдельный механизм обработки действий, например интерфейс `ActionHandler` и отдельные обработчики для чтения, записи и выполнения. Это позволит добавлять новые варианты с меньшим количеством изменений в основной логике.

### 2.3. LSP — принцип подстановки Барбары Лисков

**Где находится проблема:** в текущем проекте нет явной иерархии наследования, по которой можно было бы подтвердить нарушение LSP.

**Что не так:** на данном этапе недостаточно оснований утверждать, что принцип нарушен.

**Предлагаемое решение:** если при дальнейшем развитии появятся общие интерфейсы для пользователей, ресурсов или обработчиков действий, необходимо проверять, что их реализации сохраняют ожидаемое поведение и могут использоваться вместо базового типа без нарушения логики программы.

### 2.4. ISP — принцип разделения интерфейса

**Где находится проблема:** в проекте пока нет отдельных прикладных интерфейсов для основных операций.

**Что не так:** сейчас нельзя выделить конкретный существующий интерфейс, который заставляет классы реализовывать ненужные методы. Поэтому подтверждённого нарушения ISP нет.

**Предлагаемое решение:** при разделении приложения на компоненты создавать небольшие интерфейсы по назначению. Например, отдельно определить проверку учётных данных и проверку прав доступа, если это потребуется архитектуре проекта.

### 2.5. DIP — принцип инверсии зависимостей

**Где находится проблема:** глобальные коллекции `users`, `resources` и `permissions`, а также функция `hashPassword()` в `src/Main.kt`.

**Что не так:** логика приложения непосредственно использует конкретные коллекции данных и реализацию вычисления хеша. Если потребуется заменить способ хранения данных или механизм проверки пароля, придётся изменять код, который от этих реализаций зависит.

**Предлагаемое решение:** определить интерфейсы для получения пользователей, ресурсов и разрешений. Реализации этих интерфейсов отделить от бизнес-логики. При необходимости вынести вычисление хеша за отдельный интерфейс.

## 3. Дополнительные замечания

### 3.1. Сложность тестирования

Функция `main()` вызывает `exitProcess()` в разных ветках выполнения. Это усложняет изолированное тестирование отдельных сценариев, поскольку вызов завершает процесс.

**Предлагаемое решение:** в дальнейшем вынести основную проверку доступа в отдельную функцию или сервис, который возвращает результат проверки. Завершение процесса оставить на уровне консольного интерфейса.

### 3.2. Хранение данных

Пользователи, ресурсы и права доступа хранятся в глобальных коллекциях непосредственно в исходном коде.

**Предлагаемое решение:** отделить данные от бизнес-логики и предусмотреть возможность замены источника данных без изменения основных правил проверки доступа.

## 4. План рефакторинга

1. Выделить обработку аргументов командной строки в отдельный компонент.
2. Вынести проверку учётных данных в отдельный сервис.
3. Отделить проверку ресурсов, объёма и прав доступа.
4. Определить интерфейсы для доступа к данным и подключить их реализации.
5. Упростить тестирование за счёт возврата результатов проверки вместо немедленного завершения процесса.
6. После рефакторинга повторно выполнить имеющиеся тесты и проверить сохранение кодов возврата.

## 5. Вывод

В текущем проекте наиболее заметны проблемы с разделением ответственности и зависимостью бизнес-логики от конкретных данных. Принципы LSP и ISP нельзя считать нарушенными без дополнительных оснований. Предлагаемый план позволит сделать программу удобнее для тестирования, сопровождения и дальнейшего развития.
