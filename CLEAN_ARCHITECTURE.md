# Clean Architecture

## 1. Текущее состояние проекта

Приложение представляет собой консольную программу на Kotlin для проверки доступа к ресурсам. Вся основная логика находится в файле `src/Main.kt`.

В текущей реализации присутствуют следующие компоненты:

- `main()` — обработка аргументов командной строки и последовательное выполнение проверок.
- `User` — модель пользователя.
- `Resource` — модель ресурса и ограничение его объёма.
- `Permission` — модель разрешения на выполнение действия.
- `users` — список пользователей с хешами паролей и солью.
- `resources` — список доступных ресурсов.
- `permissions` — список разрешений.
- `hashPassword()` — вычисление SHA-256 с использованием соли.
- `hasPermission()` — проверка наличия разрешения с учётом родительских ресурсов.
- `isValidResourceFormat()` — проверка формата пути к ресурсу.

Отдельные слои приложения пока не выделены. Интерфейс командной строки, бизнес-правила и данные находятся в одном исходном файле.

## 2. Основные проблемы текущей архитектуры

1. Функция `main()` выполняет слишком много задач.
2. Бизнес-логика напрямую обращается к глобальным коллекциям.
3. Работа с аргументами командной строки связана с выполнением проверок.
4. Для тестирования отдельных сценариев приходится учитывать завершение процесса через `exitProcess()`.
5. Замена способа хранения пользователей, ресурсов и разрешений потребует изменений в существующем коде.

## 3. Предлагаемая архитектура

В дальнейшем проект предлагается разделить на четыре логических слоя.

### 3.1. Presentation — интерфейс

**Назначение:** взаимодействие с пользователем и получение аргументов командной строки.

Предлагаемые компоненты:

- `Main.kt` — точка входа в программу.
- `CliController.kt` — разбор входных данных и вызов прикладного сценария.
- `CliResultFormatter.kt` — формирование сообщений и справки.

Этот слой не должен самостоятельно реализовывать правила проверки прав доступа.

### 3.2. Application — прикладная логика

**Назначение:** организация выполнения сценария проверки доступа.

Предлагаемые компоненты:

- `CheckAccessUseCase.kt` — основной сценарий проверки доступа.
- `AuthenticateUserUseCase.kt` — сценарий проверки учётных данных.

Этот слой координирует работу компонентов и возвращает результат выполнения, не завершая процесс напрямую.

### 3.3. Domain — бизнес-модель и правила

**Назначение:** хранение основных моделей и правил предметной области.

Предлагаемые компоненты:

- `User.kt` — пользователь.
- `Resource.kt` — ресурс и ограничение объёма.
- `Permission.kt` — разрешение.
- `AccessPolicy.kt` — правила проверки прав доступа.
- `ResourcePathValidator.kt` — правила проверки пути к ресурсу.

Этот слой должен содержать основные бизнес-правила и по возможности не зависеть от консольного интерфейса и способа хранения данных.

### 3.4. Infrastructure — технические реализации

**Назначение:** реализация доступа к данным и технических операций.

Предлагаемые компоненты:

- `InMemoryUserRepository.kt` — получение пользователей из коллекции.
- `InMemoryResourceRepository.kt` — получение ресурсов.
- `InMemoryPermissionRepository.kt` — получение разрешений.
- `Sha256PasswordHasher.kt` — вычисление хеша пароля с солью.

На первом этапе можно оставить данные в памяти. Подключение базы данных для выполнения этой лабораторной не требуется.

## 4. Предлагаемая структура каталогов

После будущего рефакторинга структура может выглядеть следующим образом:

    src/
    ├── Main.kt
    ├── presentation/
    │   ├── CliController.kt
    │   └── CliResultFormatter.kt
    ├── application/
    │   ├── CheckAccessUseCase.kt
    │   └── AuthenticateUserUseCase.kt
    ├── domain/
    │   ├── User.kt
    │   ├── Resource.kt
    │   ├── Permission.kt
    │   ├── AccessPolicy.kt
    │   └── ResourcePathValidator.kt
    └── infrastructure/
        ├── InMemoryUserRepository.kt
        ├── InMemoryResourceRepository.kt
        ├── InMemoryPermissionRepository.kt
        └── Sha256PasswordHasher.kt


## 5. Интерфейсы и зависимости

Для отделения бизнес-логики от конкретных реализаций предлагается определить интерфейсы:

- `UserRepository` — получение пользователя по логину.
- `ResourceRepository` — получение ресурса по пути.
- `PermissionRepository` — получение разрешений пользователя.
- `PasswordHasher` — вычисление и проверка хеша пароля.

Интерфейсы должны располагаться в слое Domain или Application в зависимости от их назначения. Их реализации будут находиться в Infrastructure.

При таком подходе сценарий проверки доступа будет работать с интерфейсами, а не напрямую с глобальными списками.

## 6. Направление зависимостей

Зависимости должны быть направлены внутрь архитектуры:

- Presentation обращается к Application.
- Application использует бизнес-модели и интерфейсы, необходимые для выполнения сценария.
- Infrastructure реализует интерфейсы, определённые внутренними слоями.
- Domain не зависит от Presentation и Infrastructure.

Это позволит менять интерфейс или способ хранения данных с меньшим влиянием на бизнес-правила.

## 7. План перехода

1. Выделить модели пользователя, ресурса и разрешения в отдельные файлы.
2. Вынести проверку пути и правила доступа в Domain.
3. Создать сценарий `CheckAccessUseCase`.
4. Определить интерфейсы репозиториев и проверки пароля.
5. Перенести текущие коллекции и реализацию SHA-256 в Infrastructure.
6. Оставить в `Main.kt` только настройку компонентов и запуск приложения.
7. Проверить все существующие тестовые сценарии и коды возврата.

## 8. Вывод

Разделение на Presentation, Application, Domain и Infrastructure позволит отделить интерфейс от бизнес-логики и хранения данных. Для текущего небольшого проекта это планируемое улучшение, а не обязательное усложнение программы. Реализацию архитектуры можно выполнять постепенно после завершения анализа.
